## Decision and evidence

`go-htmx4/kit/i18n` is the one part of that repo that names nothing of it. It was
built there, but nothing about it is Remy's or htmx's: it is CLDR data, ICU
MessageFormat, and Intl-exact formatting proved against a browser oracle. Every
app on the stack will want it, and no app should have to copy it. It moves into
`github.com/joeblew999/dev`, the tool every repo on the stack already pins.

**What actually moves.** The byte count is misleading — `kit/i18n/cldr` is
112,296 lines across 15 files, every one `// Code generated`, produced by
`cldrgen` from `I18N_LOCALES`. It is output, not source, and is regenerated per
app for the locales that app ships. It does not move.

| Source | Files | Lines | What it is |
|---|---|---|---|
| `kit/i18n` | 25 | 7,766 | the runtime library: locale, tag, plural, number, decimal, datetime (×4), duration, list, message, relative, timezone, unit, zones |
| `kit/i18n/cldrgen` | 13 | 2,625 | CLDR tables from cldr-json, pinned |
| `kit/i18n/intltest` | 9 | 2,005 | the conformance cases |
| `kit/i18n/msggen` | 3 | 820 | ICU MessageFormat catalogs → typed Go accessors |
| `kit/i18n/internal/goemit` | 1 | 95 | Go source emission |
| `cmd/{cldrgen,msggen,i18npins,intloracle,intlbrowsers}` | 5 | 294 | thin flag wrappers, 33–123 lines each |
| **Total** | **56** | **13,605** | |
| ~~`kit/i18n/cldr`~~ | ~~15~~ | ~~112,296~~ | **generated per app — does not move** |

**It ports with zero new dependencies.** `go list -deps` over the four packages
returns the standard library plus `github.com/BurntSushi/toml` — and `dev/go.mod`
already requires `github.com/BurntSushi/toml v1.6.0`, the identical version.
Toml is `msggen`'s alone: the library itself needs nothing outside the standard
library. Nothing else changes in `dev`'s module graph.

**The import path is data, not only an import.** Eight `go-htmx4` sites inside
`kit/i18n` are not import statements, and they do not all rewrite the same way:

| Site | What it is |
|---|---|
| `internal/goemit/goemit.go:12` `ImportPath` | matched against `reflect.Type.PkgPath()` to decide whether a value is written as `i18n.T` |
| `cldrgen/emit.go:15` `importPath` | the same constant again, in a second emitter that does not import `goemit`; also the `import` line written into every generated file |
| `cldrgen/cldrgen.go:5` | doc-comment example (`go run …/cmd/cldrgen`) |
| `intltest/cases.go:5` | doc-comment example (`go run ./cmd/intloracle`) |
| `cldrgen/cldrgen.go:30`, `cldrgen/sources.go:44`, `sources.go:54` | the cache directory: three sites, not one |
| `intltest/cases.go:32` | "the locales the cases cover (the go-htmx4 app's shipped set)" — see below |

The two constants are the load-bearing ones. They must equal the moved library's
real path or `goemit` silently stops qualifying types, and they are written
verbatim into the `import` line of all 15 generated files — which is why I5 is
worded as it is. Nothing makes the two agree today; either `cldrgen/emit.go`
starts importing `goemit.ImportPath`, or a test holds them equal.

**`intltest.Locales` is the app's locale set.** Fourteen ids, hardcoded, and the
2.2 MB committed golden records Intl's output for exactly those. Read as "what
this app ships" it breaks `dev`'s "nothing project-specific" rule; read as "the
locales the library's correctness is proven against" it is a property of the
library and belongs here. It is the second, and the comment is rewritten to say
so. What a consumer ships is `I18N_LOCALES` in its `mise.toml`, which is what
`generate` and `messages` take; the conformance set is not that and never was.

**The one design constraint.** `kit/i18n` is a *runtime library*: the app imports
it and it ships in the Worker under TinyGo. The five commands are *tooling*: they
fetch over the network, shell out, and drive real browsers. These must not be the
same Go package, or an app's Worker build would pull `os/exec` and a browser
driver through its i18n import. This is the same rule as PR 0 of
`2026-09-16_0700_toolchain.md` item 3 ("the tool layer is TinyGo-clean by
construction"), applied to the tool's own module.

**The constraint the tool has never had: `dev` becomes importable.** Every repo
pins `dev` as a signed binary today; nothing imports it. After this, an app that
imports `dev/i18n` carries `github.com/joeblew999/dev` in its `go.mod`, and three
things follow. `dev`'s `go 1.27.1` becomes a floor for every consumer (go-htmx4
declares `go 1.27`). One tag versions both a developer tool and a runtime
library, so a breaking change to a verb and a breaking change to `i18n.Locale`
share a version line. And the module zip carries `testdata/golden/workerd.json`
(2.2 MB) into every consumer's module cache. None of it blocks the move; all of
it is new, and a release note should say which half of the module a version
broke.

So, in `dev`'s existing idiom — one `main.go`, one package per verb beside it,
`internal/` for what they share, and no `cmd/` or `pkg/` directories anywhere:

```
dev/
  i18n/                    package i18n — the runtime library. What apps import.
                           Stdlib only. TinyGo-clean. Never imports the below.
    cldrgen/               CLDR generator (net/http, pinned sources)
    msggen/                ICU MessageFormat → typed accessors (toml)
    intltest/              conformance cases (net/http, os/exec: drives browsers)
    testdata/golden/       workerd.json, the recorded Intl oracle
    internal/goemit/       Go source emission
    gen/                   package gen — Run + Usage, the `dev i18n` verb.
                           Imports the generators; nothing imports it but main.go.
  main.go                  verbs["i18n"] = {gen.Run, gen.Usage}
```

An app imports `github.com/joeblew999/dev/i18n` and gets the library and nothing
else; `dev` links `gen` and gets the tooling. The alternative — a top-level
`dev/i18ngen` package — reads the same to `main.go` but scatters one aspect
across two directories; `i18n/gen` keeps it in one.

**`dev i18n` is a sub-verb group**, exactly like `dev session` and `dev secrets`:
a `Usage` const, `Run(verb, args, stdout, stderr) error`, `cli.Usagef` for a bad
call. `dev skill` renders the tool's Claude Code skill from the verbs' own usage,
so the manual updates itself when this lands.

| Today | Becomes |
|---|---|
| `i18n:generate` → `cldrgen -locales -out [-pkg -tag -cache -currencies -q]` | `dev i18n generate DIR [--locales LIST] [--pkg N] [--tag T] [--cache D] [--currencies LIST] [-q]` |
| `i18n:golden` → `intloracle -out [-workerd -port]` | `dev i18n golden DIR [--workerd BIN] [--port N]` |
| `i18n:messages` → `msggen -dir -out -locales [-pkg -source]` | `dev i18n messages DIR [--out DIR] [--locales LIST] [--pkg N] [--source LOC]` |
| `i18n:verify` → inline bash in `tasks/i18n.toml` | `dev i18n verify DIR` — **open, see step 2** |
| `i18n:pins` → `i18npins [-workerd -latest -write -strict]` | `dev i18n pins [--workerd V] [--latest] [--write] [--strict]` |
| `i18n:browsers` → `intlbrowsers -browsers -golden -out [-examples]` | `dev i18n browsers DIR [--browsers LIST] [--golden FILE] [--out DIR] [--examples N]` |

The flags are not trimming to taste. `--latest --strict` *is* the scheduled
"time to move the pins" check and nothing else performs it; `generate`'s
`--out`, `messages`' `--dir` and its `--out` are three different directories, so
DIR-first covers one of them at most; `golden`'s `--workerd` is how a pinned
binary gets named. `dev skill` renders the manual from `Usage`, so a flag
dropped here disappears from the manual without a word.

`ci/i18n-verify.sh` does not survive the move — "no shell scripts behind tasks"
is `dev`'s rule — but it is worth being exact about what it is. It is not
verify's implementation and `i18n:verify` does not call it: it is a CI driver
that installs mise and then runs `mise run i18n:verify`, `i18npins -latest
-strict`, and `mise run i18n:browsers`. Its three steps become three `dev i18n`
calls in a workflow, and the `-latest -strict` one is the step that must not be
lost in the move.

**Not in this plan, and no longer proposed:** `kit/cfdeploy` and `kit/cftail`
(deploy and tail a Worker through the REST API, no wrangler). They looked like
the strongest candidates for `dev` until PR 0 of `2026-09-16_0700_toolchain.md`
was read: that plan adopts pinned wrangler and **deletes `cmd/deploy` and
`workerd/`**. Code go-htmx4 is removing is not code the tool should adopt.

## Work

1. **Move the library.** `go-htmx4/kit/i18n` → `i18n/`, subpackages and `testdata/`
   with it, tests included (`conformance_test.go`, `datetime_test.go`,
   `locale_test.go`, `zones_test.go`, `intltest`). Rewrite the eight `go-htmx4`
   sites tabled above: the two doc-comment examples become `dev i18n generate`
   and `dev i18n golden`; the three cache sites become
   `<user cache dir>/dev/cldr-json/<tag>`; `intltest.Locales`' comment says what
   the set actually is; and both `ImportPath` constants become
   `github.com/joeblew999/dev/i18n`. No behaviour change except the last, which
   changes generated output by one line per file.
2. **Fold the five commands into `i18n/gen`.** Each is a flag wrapper over a
   package that already does the work; they become one `Run` with six sub-verbs
   and one `Usage`, carrying the whole flag surface above. Every error names its
   fix, per `dev`'s rule.

   **The open question is `verify`.** It is not, today, a verb with a branch in
   it. It is `go test -count=1 -run 'TestPinsMatchWorkerd|TestTablesReproduce|
   TestChromiumRegionNames' ./kit/i18n/cldrgen`, the same over
   `TestGoldenReproduces|TestKnownEvidence|TestConformance` in `./kit/i18n`, and
   `go test -run TestReferencePins .` in the app itself. The first two sets move
   into `dev`, where a consumer has a signed binary and no source tree and so
   cannot `go test` them. `dev i18n verify DIR` as drawn cannot be built. Two
   ways out:

   - **(a) Reimplement verify as code.** What those tests assert becomes what
     the verb does: regenerate the tables to a temp dir and compare bytes,
     re-record the golden with the pinned workerd and compare, check the pins,
     hold the known-difference evidence. The tests then call the same functions,
     so nothing is asserted twice. More work, and `verify` means one thing from
     any repo.
   - **(b) Split it.** The library's own reproduction becomes `dev`'s CI — `go
     test` in this repo, where the source is — and `dev i18n verify DIR` keeps
     only what is about the consumer: that its committed `cldr/` matches its
     `I18N_LOCALES`, which is `TestReferencePins` today. Cheap, and a consumer
     can no longer prove the tool's own data reproduces from the pins.

   (a) is the one worth building — the verb is the reason `ci/i18n-verify.sh`
   can die — but (b) is the smaller landing and could come first. Decide before
   writing `Usage`: the answer changes what `verify DIR` means.
3. **Wire it.** `verbs["i18n"] = {gen.Run, gen.Usage}` in `main.go`; regenerate
   the skill (`dev skill`) and check it in.
4. **Decide where the data pins live.** `cmd/i18npins` edits `mise.toml`
   (workerd) and `kit/i18n/cldrgen/sources.go` (Workerd, ChromiumICU). The
   cldr-json and ICU pins are properties of the *library*, so they move to
   `dev/i18n/cldrgen/sources.go`; the workerd pin stays a property of the
   *repo being checked*, read from its `mise.toml`. `dev i18n pins` reports both
   and `--write` moves the library's. `--latest` and `--strict` come with it:
   "the newest workerd release builds with a different Chromium ICU, so it is
   time to move the pins" is `pins --latest --strict`, and it is the one thing
   `ci/i18n-verify.sh` does that nothing else does.
5. **go-htmx4 becomes the first consumer.** `kit/i18n` deleted; imports in
   `i18n.go`, `board.go` and `i18n_test.go` repointed to
   `github.com/joeblew999/dev/i18n`; `kit/i18n/cldr` regenerated in place as
   `locales/cldr` (or wherever step 1's `-out` lands it) and still committed;
   `tasks/i18n.toml` rewritten to six `dev i18n` calls; `ci/i18n-verify.sh`
   deleted; `cmd/{cldrgen,msggen,i18npins,intloracle,intlbrowsers}` deleted.
   Three more that the first draft missed: `i18n_test.go`'s `TestReferencePins`
   reads `mise.toml` against the `cldr/` path, so it repoints or moves according
   to step 2's answer; `tasks/app.toml` greps `I18N_LOCALES` out of `mise.toml`
   by hand and keeps working, because the var stays where a repo supplies it;
   and `go.mod` gains `github.com/joeblew999/dev` with its `go` directive rising
   from 1.27 to 1.27.1.
6. **Release and pin.** `mise run release <version>` in `dev`, bump the pin here.
   Nothing lands in go-htmx4 until the tool is released; this is the last step,
   not the first.

## Where this plan lives

`dev` had no plan directory; it has one now, and this is its first plan. The
convention is go-htmx4's: a date-time prefix on every file, finished plans move
to `done/` (`.plans/README.md` there says it). The tool's own origin plan is
`grok-oauth-proxy/.plan/dev-tool.md` ("one dev tool for every repo on this
stack", DONE 2026-09-17) — written before `dev` was a repo of its own, which is
why it sits in the repo that grew it. From here, `dev`'s plans live in `dev`.

Steps 5–6 land in go-htmx4; that repo's `.plans/` gets its own entry when they
start, pointing back here.
