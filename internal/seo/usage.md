### What Google asks of a page

Three things, and they share one declaration so they cannot disagree: `write`
produces the files a site needs, `validate` checks those files with no network
at all, and `check` runs the external checkers against a deployed URL.

Every file `write` produces declares the check that proves it good, and
`validate` runs that same check — so an artifact cannot pass when it is written
and fail when it is checked. Nothing is generated by a library: no Go package
writes robots.txt, every one of them is a parser, and the packages that write
the rest each cost a dependency this tool will not carry to render six tags.

`check` takes a URL rather than a directory, because what Google sees is what
the deployed site serves, not what the source says it will. So it runs after a
deploy, not in `check` and not in `validate` — `validate` is what `deploy` runs
first, and on a first deploy there is nothing yet to crawl. A repo wires it as
its own task, the way `wait` is chained after a deploy.

The checkers are pinned in `mise.toml`, run at once, and merge in a fixed
order, so two runs of the same site are comparable. No checker is made to share
a shape, because they do not have one: one counts pages, one counts links, one
scores a site. The report carries what they all have — an issue, where it is,
how to fix it — and each checker's own output is written beside the report and
linked from it, so nothing is lost to the merge. A checker that is missing or
fails is listed with the reason and with what it would have told you; one
unpinned tool is not a reason to learn nothing about the page.

Every issue carries the fix and the Google page that explains why, because a
code and a severity say what is wrong and not what to do about it. Where one
of the files this can write would close the gap, the issue names that file and
the report ends with the command that writes it — so a check is a route to a
fix and not only a list of faults. An issue that names no file is content
rather than configuration: a broken link is fixed in the page, or upstream.

`can` lists everything this verb can write and check, what each needs, what it
gives and whether it is installed. It runs nothing and touches no network, so
it is what to read first.

`--json` answers as JSON instead of prose and `--out` writes those same bytes
to a file, a bare name landing in `.reports/` with the sub-reports beside it.
`--record` keeps each run in a directory and says what was fixed and what is
new since the last one. `--fail-on` decides which severity fails, so the same
command is a report on a laptop and a gate in CI.
